# FIXP in fix2

What fix2's FIX Performance Session Layer engine speaks, how it is split
into packages, what it guarantees and stores, and how it reads the places
where the standard contradicts itself, for
[issue #3](https://github.com/sylr/fix2/issues/3). The implementation
follows it, in the [increments](#increments) at the end, of which the
table says which are done.

The standard is [FIXP 1.0](https://www.fixtrading.org/wp-content/uploads/download-manager-files/FIX_Performance_Session_Layer_V1.0.pdf)
(FIX Technical Standard, April 2021). Section numbers below (§) are its own.

## Profile

The engine is generic: it serves no venue in particular, and plays both
roles, client and server.

| Layer | fix2 v1 |
|---|---|
| Transport | TCP, with or without TLS, through the `transport` package; one session per connection (no multiplexing) |
| Framing | Simple Open Framing Header ([SOFH](https://github.com/FIXTradingCommunity/fix-simple-open-framing-header)): a 4-byte message length, header included, and a 2-byte encoding type, both big-endian |
| Session messages | SBE 1.0 little-endian (SOFH encoding type `0xEB50`), from the FIXP schema below |
| Application messages | SBE 1.0 little-endian, opaque to the engine; any schema but the FIXP one |
| Flows | Recoverable, Idempotent, Unsequenced and None, in either direction (see [Flows](#flows)) |

Out of scope: multicast and UDP (`Topic`), multiplexing (`Context`),
in-band template delivery (`MessageTemplate`), exchange dialects (CME
iLink 3, B3 BOE and the like), high availability.

## Packages

| Package | Holds |
|---|---|
| `sofh` | Frame reader with a length bound, failing closed: a malformed frame ends the connection, the reader never resynchronises. Frame header append. |
| `fixp` | Protocol values: `SessionID` (UUID), `FlowType`, the reject and termination codes, errors. |
| `fixp/internal/codec` | The session messages' SBE codecs, generated by `fix2gen sbe` from the pinned schema and committed. |
| `fixp/session` | The engine: `Client`, `Server`, `Session`, `Config`, `Handler`. |
| `fixp/store` | What a session persists (see [Persistence](#persistence)), with `memstore` and the `storetest` conformance suite. |
| `fixp/tests/...` | End-to-end, interoperability and benchmark suites. |
| `cmd/fix2gen` | The code generator: `fix2gen tagvalue`, formerly `fixgen`, and `fix2gen sbe`; the generators themselves are `internal/gen/tagvalue` and `internal/gen/sbe`. |

`fixp` shares `transport` and `internal/hrtimer` with the FIX engine, and
nothing else: `fix/session/store` keeps its FIX-shaped contract. Generated
SBE codecs are self-contained, without a runtime package of fix2's; the
SBE schema parser stays internal to the generator until something else
needs it.

## The schema

The session messages come from `SBEschemaForFIXP.xml` of the FIX Trading
Community's
[fixp-specification](https://github.com/FIXTradingCommunity/fixp-specification)
repository, at commit `af0e9d7eca87b2b7a9a1ace996dd3076013e37d2`, path
`v1-0-STANDARD/resources/SBEschemaForFIXP.xml`, SHA-256
`e14417224cbd625ca21fab118ef8ac1776a0ad7c70799950e1d3e807f4dcdac1`. It
is committed as published, as
[`fixp/internal/codec/SBEschemaForFIXP.xml`](../fixp/internal/codec/SBEschemaForFIXP.xml);
where it disagrees with the standard's text, this document says what the
engine does, and the file is not edited.

Schema id 2748, version 0, little-endian. The SBE message header is four
`uint16`: blockLength, templateId, schemaId, version.

| Id | Message | Engine |
|---|---|---|
| 1 | Negotiate | session |
| 2 | NegotiationResponse | session |
| 3 | NegotiationReject | session |
| 4 | Topic | multicast only: a protocol violation on a point-to-point session |
| 5 | Establish | session |
| 6 | EstablishmentAck | session |
| 7 | EstablishmentReject | session |
| 8 | Sequence | session |
| 9 | Context | multiplexing only: a protocol violation here |
| 10 | UnsequencedHeartbeat | session |
| 11 | RetransmitRequest | session |
| 12 | Retransmission | session |
| 13 | RestransmitReject (sic) | session |
| 14 | Terminate | session |
| 15 | FinishedSending | session |
| 16 | FinishedReceiving | session |
| 17 | Applied | application message: consumes a sequence number (§4.8.1) |
| 18 | NotApplied | application message: consumes a sequence number (§4.8.2) |
| 19 | MessageTemplate | out of scope: checked well-formed and ignored, it "may be sent at any time" (§3.6), in the handshake too, whose deadline it does not extend |

A message is classified by its SOFH encoding type, then its schema id,
then its template id: Applied and NotApplied share the session schema but
are application messages, sequenced like any other. An application schema
must not use id 2748, and its message header must start as SBE's standard
one does, with the four `uint16` above in that order: the engine reads
the schema id of every message there. A frame of another encoding, too
short for a header, a Topic, a Context, or a template the schema does
not define, is a protocol violation (§4.4).

Where the schema and the text differ:

- `Context.NextSeqNo` is optional in the text (§3.5.3), required in the
  schema. Context is out of scope.
- `Topic` has a `KeepaliveInterval` in the schema the text does not list
  (§5.1.1.1). Topic is out of scope.
- Template 13 is spelt `RestransmitReject`, as are some headings of the
  text (`RestransmitRequest`, `Restransmission`). The generated codec,
  internal, keeps the schema's spelling; fix2's API spells it correctly.
- `Establish.NextSeqNo` is described in the text as "for re-establishment
  of a recoverable server flow only, the next application sequence number
  to be produced by the client" (§4.3.1), in the schema as "for
  re-establishment of a recoverable flow only, the next application
  sequence number to be produced by the client". The value is the
  client's; see [Establishment](#establishment) for when the engine sends
  it.
- Credentials and Reason are optional in the text; SBE has no absent
  `data` field, so an empty one stands for absent. (Topic's Classification
  and MessageTemplate's Template are required, both out of scope.)

## Flows

Each direction of a session carries one flow (§3.4.4):

- **Recoverable**: exactly once. The receiver asks for what it missed,
  the sender retransmits it from its store.
- **Idempotent**: at most once. The receiver drops duplicates and tells
  the sender about gaps (NotApplied); recovery is the application's.
- **Unsequenced**: best effort, no sequence numbers.
- **None**: no application message in that direction.

Every pair of client flow and server flow is supported but None and None
(§3.4.4.1). A server is configured with the client flows it accepts, and
answers others with NegotiationReject `FlowTypeNotSupported`. The pair the
standard recommends, and the one fix2 tests most, is an Idempotent client
flow and a Recoverable server flow (§4.8.2, §7.1.3): orders in, execution
reports and NotApplied out, the client able to learn with certainty which
of its requests were accepted.

A Recoverable flow needs a store at its sender, holding the messages it
may retransmit. An Idempotent flow needs one too, holding only the next
sequence number: see [Persistence](#persistence).

## Lifecycle

### Negotiation

A logical session is identified by a UUID the client chooses (§3.4.1). The
client sends Negotiate once per session (§4.2): its session ID, a
timestamp, its flow and its credentials. The server answers
NegotiationResponse, with its own flow, or NegotiationReject.

- Session IDs are RFC 4122 version 4 UUIDs (§3.4.1): the engine generates
  them, and a server rejects any other, the nil UUID included, with
  `Unspecified` (§7.1.7.3).
- Timestamps are nanoseconds since the Unix epoch. A server rejects one
  that cannot be (before 2000, or further than a configured skew from its
  clock) with `Unspecified` (§7.1.7.4).
- A session ID is unique "for all time" (§3.4.1). A server rejects one it
  has already negotiated with `DuplicateId`, for as long as it remembers
  finalized sessions (a configured retention: "the server may have a
  practical limit of session history", §6.3).
- A client ignores a response whose session ID or request timestamp is
  not its request's (§7.1.7.5), and one that does not come within its
  negotiation timeout (§7.1.7.6); it then negotiates again, under a new
  session ID. It records the session only once negotiated: until then,
  `Send` fails, its messages belonging to no settled session.
- A server retires a session negotiated and never established within a
  configured timeout: a client whose NegotiationResponse was lost
  negotiates again under a new ID, and the first must not hold a session
  slot. It retires any session on demand too. A retired session is
  finalized, its flows as they were, its ID refused like a finalized one's.
- A server authenticates the owner of a session at Negotiate and stores
  it; an Establish authenticated as another owner is rejected with
  `Credentials`: a session ID alone gives no one its session.
- The server's Credentials in NegotiationResponse, by which it could
  authenticate itself (§4.2.2), are not supported: the server sends none,
  the client ignores any. TLS authenticates a server.

### Establishment

The client sends Establish on every connection, to bind the session to it
(§4.3): its session ID, a timestamp, its keepalive interval, its next
sequence number and its credentials. The server answers EstablishmentAck,
with its own keepalive interval and next sequence number, or
EstablishmentReject.

- `NextSeqNo` is the sender's own: the next sequence number the client
  will send in Establish, the server's in EstablishmentAck (§4.3.1,
  §4.3.2). The engine fills it in EstablishmentAck for a Recoverable server
  flow, the first establishment included (§4.3.2: "For a recoverable
  server flow only"), in Establish on re-establishment of a Recoverable
  client flow only (§4.3.1, read as the schema words it: see [the
  contradictions](#where-the-standard-contradicts-itself)); an Idempotent
  flow starts with a Sequence (§4.8: "The start of an idempotent flow must
  be initiated with a Sequence message"). Received, it numbers a
  Recoverable flow, on a first establishment too, as the examples send it
  (§7.2.1); for another flow it is accepted and ignored, an Idempotent
  flow's messages before a Sequence a protocol violation. Its absence is
  accepted.
- A client compares the server's `NextSeqNo` with what it received, and
  asks for what it missed (Recoverable) at once (§4.3.2). A `NextSeqNo`
  below what it already received means the server lost messages it had
  sent: the client terminates (§7.3.3).
- A server answers an Establish for a session it never negotiated, or one
  finalized, with `Unnegotiated` (§7.2.5.1); for a session established on
  another connection, with `AlreadyEstablished` (§7.2.5.2): the earlier
  binding stays, until it terminates or its keepalive lapses. An Establish
  again on the connection the session is established on is redundant, and
  gets `AlreadyEstablished` too, the binding staying (§4.3.3); one for
  another session there is a protocol violation. A keepalive
  interval outside the configured range gets `KeepaliveInterval`
  (§7.2.5.4); a client terminates on an EstablishmentAck whose interval
  is outside its own range, and its `Run` ends: both roles bound the
  peer's (`MinKeepalive`, `MaxKeepalive`: "Counterparties may agree on a
  valid range for KeepaliveInterval", §4.3.1). A session ID that is not a
  version 4 UUID, a timestamp out
  of range, or a `NextSeqNo` below what the server received, `Unspecified`
  (§7.2.5.5, §7.2.5.6, and §7.3.3 the other way). A session the
  application blocks, its `Authenticate` hook returning a
  `*fixp.EstablishmentRejectedError`, gets that code, such as
  `SessionBlocked` (§7.2.5.3), which a client keeps trying, a block being
  temporary; `Unnegotiated`, `Credentials` and `KeepaliveInterval` end its
  `Run`.
- A client ignores an EstablishmentAck or a NegotiationResponse that is
  not its request's, by session ID or timestamp, and connects again once
  its handshake timeout lapses: under the same session ID for an
  Establish (§7.2.5.8, §7.2.5.9), a new one for a Negotiate (§7.1.7.5,
  §7.1.7.6).
- The server authenticates the client at Negotiate and again at every
  Establish, with its credentials and the connection's identity (TLS
  state, or the principal a `transport.PrincipalConn` reports).
- A session can be re-established on a new connection, without
  negotiating again, until it is finalized (§3.4.3, §4.1).

### Transfer

Sequence numbers are implicit (§3.5.1): a Sequence message gives the next
sequence number, and every application message after it takes the next
one. Sequence, EstablishmentAck and Retransmission set the numbering; any
other session message a sender sends ends it (§3.5.4, §7.4.1.1).

On a Recoverable or Idempotent flow:

- The engine sends a Sequence before its first application message after
  establishment, and before its next application message after any
  session message of its own that does not set the numbering, such as a
  RetransmitRequest.
- Retransmitted messages follow their Retransmission directly; real-time
  messages after a batch follow a Sequence (§4.6.2, §4.6.2.2). The
  retransmission and real-time positions are tracked apart.
- It accepts application messages of a Recoverable flow right after the
  peer's EstablishmentAck or Establish when it carries `NextSeqNo`
  (§7.4.1); without it, and always on an Idempotent flow (§4.8), a
  Sequence has to come first. After a retransmitted batch, it requires a Sequence before
  real-time messages: numbering them on would number them wrong.
- A Sequence whose `NextSeqNo` is lower than expected ends the connection
  (§7.4.1.2). A higher one is a gap (§7.4.1.1).
- An application message whose numbering is not known (no `NextSeqNo`,
  no Sequence yet) is a protocol violation (§3.5.1).

On an Unsequenced or None flow, the engine never sends Sequence, and
receiving one is a protocol violation (§3.5.1).

### Keepalive

Each side sends a heartbeat in each of its own intervals in which it sent
no application message: the client at the interval it gave in Establish,
the server at the one it gave in EstablishmentAck (§4.5). The heartbeat is
Sequence on a Recoverable or Idempotent flow, UnsequencedHeartbeat on an
Unsequenced or None flow, and FinishedSending while finalization waits
for its answer (§4.5, §4.7.1).

Each side watches the other's interval: silence beyond the peer's interval
times a leniency factor (`KeepaliveLeniency`, 1.5 by default, at least 1
and finite: the standard recommends "some leniency" and sets none, §4.4)
ends the connection. Each bounds the peer's interval (`MinKeepalive`,
`MaxKeepalive`, 100ms and 1m by default), and the configuration the
product of the leniency and `MaxKeepalive`, which must fit a
`time.Duration`. `ToleratePeerWithoutKeepalives` keeps the connection
however long the peer is silent, as Silverflash, which sends no
heartbeat, needs: a departure from §4.5, "Each peer must send a
heartbeat message during each interval in which no application messages
were sent". TCP_NODELAY is set (§4.5).

### Termination

Terminate unbinds the connection; the session lives on (§4.4).

- On a Terminate, the engine answers Terminate and sends nothing more
  (§4.4.1). The side that sent the first Terminate closes the connection
  on the answer, or after one keepalive interval without it (§4.4.1,
  §4.4.2).
- Terminating on an error (protocol violation, lapsed keepalive, a
  malformed frame) does not wait for the answer (§7.3.1).
- After a Terminate, the connection is closed: a new Establish goes on a
  new connection (§4.4.2). Messages after a Terminate are ignored (§4.4).
- Codes: `Finished` for a graceful unbinding, `ReRequestInProgress` for a
  RetransmitRequest while one is outstanding (§4.6.4),
  `ReRequestOutOfBounds` for one beyond what was sent (§6.3),
  `UnspecifiedError` for everything else, with a reason. A Terminate whose
  code is not one of these is malformed (SBE §4.15): it is answered
  `UnspecifiedError`, never with its code.

### Finalization

FinishedSending ends a flow, FinishedReceiving acknowledges it; once both
flows are finished, the session is (§4.7, §7.5.1). Its session ID is then
no longer valid, nor its messages recoverable. The standard also lets the
side that started finalization terminate after one FinishedReceiving
(§4.7.2); see [the contradictions](#where-the-standard-contradicts-itself).

- `Session.Finish` sends FinishedSending, after every message `Send`
  accepted, with `LastSeqNo` on a Recoverable or Idempotent flow and
  without on an Unsequenced or None one; `Send` fails after it. The
  engine sends it again on every establishment until FinishedReceiving
  comes, and it is the heartbeat until the session terminates (§4.7.1,
  §7.5.2). Meanwhile the engine still answers RetransmitRequests (§7.5.5);
  gaps it finds on the peer's flow then go unreported, no application
  message following FinishedSending.
- On the peer's FinishedSending, the engine first completes the flow:
  RetransmitRequest up to `LastSeqNo` on a Recoverable flow, NotApplied for
  a gap on an Idempotent one (§4.7.1, §7.5.3). It then tells the handler,
  which may send its last messages, or refuse (the connection terminated,
  the flow unfinished); then it finishes its own flow, behind every
  message accepted, and answers FinishedReceiving: nothing of its follows
  (§6.3). A FinishedSending again is answered again. A `LastSeqNo` missing
  on a sequenced flow, changed, or below messages received is a protocol
  violation, as is an application message after it, or FinishedReceiving
  for a flow not finishing.
- Once both sides have sent and received FinishedReceiving, either
  terminates (§7.5.1): the engine sends Terminate `Finished` at once, and
  two Terminates crossing each take the other as its answer.
- The session is finalized once that Terminate exchange completes: the
  peer heard everything. Finalizing as soon as both flows were finished
  could strand a peer whose FinishedReceiving was lost in a crash. A
  connection ending before the exchange leaves the session
  re-establishable, both flows finished, for the exchange to happen on the
  next one; a server retires it, unbound so for its unestablished timeout,
  and a client told `Unnegotiated` then knows it over.
- A Terminate before both flows are finished is answered, and the session
  stays re-establishable, the finished flow staying finished.
- Each flow's finalization is stored, and synced, as it happens (see
  [Persistence](#persistence)): a restart neither reopens a finished flow
  nor forgets a FinishedSending awaiting its answer.

## Recovery

### Recoverable flow

The sender stores every application message before it writes it to the
connection, with the same rule the FIX engine follows: a message is
synced to its store before it is sent.

The receiver detects a gap from a Sequence, a Retransmission or an
EstablishmentAck, and sends RetransmitRequest for it (§4.6.1):

- One request at a time per session (§4.6.1). The answer is matched by
  its `RequestTimestamp`; a Retransmission or RetransmitReject matching no
  outstanding request is a protocol violation.
- The sender may answer with a partial batch; the receiver requests the
  rest (§4.6.2.2). The engine as sender answers a request with one
  batch, of a configured size at most: a Retransmission then its
  messages, real-time messages following after a Sequence. A second
  batch for the same request, as §7.4.4.2 shows, the engine neither sends
  nor accepts (see [the contradictions](#where-the-standard-contradicts-itself)).
- Messages after a gap are kept, up to a configured bound, and delivered
  in order once the gap is filled (§4.6.1). Beyond the bound they are
  dropped and requested again: they are recoverable.
- As sender, the engine terminates on a request beyond what was sent,
  wholly or in part, `ReRequestOutOfBounds`: "it is a violation to request
  a retransmission of a message with a sequence number that has not been
  sent yet" (§6.3). `RejectRetransmitRequestBeyondSent` answers it
  RetransmitReject `OutOfRange` instead, as the examples do (§7.4.5.1,
  §7.4.5.2), §6.3's "should be immediately terminated" leaving the
  choice. A request for messages sent and no longer kept gets
  RetransmitReject `OutOfRange`, reason "no longer available" (§7.4.5.5);
  one for no message `OutOfRange` too; one for another session
  `InvalidSession`. It
  never answers `RequestLimitExceeded`: it sends a partial batch instead.
  A second request while one is outstanding gets Terminate
  `ReRequestInProgress` (§4.6.4, §7.4.4.1). A RetransmitRequest on a flow
  that is not Recoverable ends the connection (§4.6.1).
- As receiver, on RetransmitReject `RequestLimitExceeded` it asks again
  for fewer messages; on `InvalidSession` it terminates, the request
  having carried its own session ID; on `OutOfRange` the messages are
  lost. The handler is told their range and decides: skip them and go on,
  or end the session. Nothing is skipped without it.

### Idempotent flow

The receiver drops a message whose sequence number it has already seen,
silently (§4.8). On a gap it sends NotApplied with the missing range at
once, and keeps accepting the messages after it (§4.8.2). NotApplied goes
on the receiver's own flow, as an application message consuming a
sequence number, so only a Recoverable or Idempotent return flow carries
it: on an Unsequenced or None return flow, gaps go unreported to the
sender, and only the receiving handler learns of them. The sender's
handler gets NotApplied and
decides: send the operations again, under new sequence numbers, send
others, or nothing (§4.8.2).

The engine sends Applied only when the application does: the standard
prefers application-level acknowledgements, such as ExecutionReport, and
keeps Applied for where none exists (§4.8.1). An Applied received for our
flow when it is not Idempotent, or beyond what we sent, goes to the
handler, a warning logged: FIXP makes a violation of NotApplied on such a
flow (§4.8.2), not of Applied.

## Delivery guarantees

| Inbound flow | The handler gets each message | Because |
|---|---|---|
| Recoverable | at least once, in order, of every message the sender still holds; a range it no longer holds goes to the handler as lost (see [Recovery](#recoverable-flow)) | The engine records a message as delivered after the handler returns: a crash in between delivers it again after the restart. The application deduplicates by session ID, direction and sequence number. |
| Idempotent | at most once, in arrival order | The engine records a message as received before the handler sees it: a crash in between loses it, without NotApplied, and the sender learns of it by the absence of its acknowledgement (§4.8). |
| Unsequenced | as it comes | |

An application needing exactly-once effects records the sequence numbers
it applied in its own transactions. A later increment may let it take
over the engine's checkpoint.

A handler failing a message terminates the connection: on a Recoverable
flow the message is not recorded as delivered, and is asked for again on
the next establishment; on an Idempotent one it was admitted, and is not.

`Send` assigns the next sequence number, and the message belongs to the
flow from then on: cancelling its context does not withdraw it. On a
Recoverable flow, `Send` returns once the message is stored; on an
Idempotent one, once the next sequence number is. On an Unsequenced flow
it assigns none, on a None flow it fails. A store failing halts the
session; the store, opened again, tells what was stored.

## Persistence

A session's store holds:

- its metadata, recorded once negotiated: role, session ID, flows, the
  owner on a server, when it was negotiated and first established; and for
  each direction whether its flow is finishing (FinishedSending sent or
  received, with its `LastSeqNo`) or finished (FinishedReceiving sent or
  received), and whether the session was finalized or retired. Keepalive
  intervals belong to a connection, and are not stored;
- outbound: the next sequence number to assign; on a Recoverable flow, the
  messages, with a retention bound;
- inbound, on a Recoverable flow: the resolved frontier, every sequence
  number up to it delivered to the handler, which returned, or skipped
  with its consent; recovery resumes after it, what was received beyond it
  being kept in memory only;
- inbound, on an Idempotent flow: the highest sequence number admitted,
  which moves past gaps once NotApplied reports them.

Each write is atomic, a crash included: a message stored with the next
sequence number, the flows' finalization.

Every change is durable before what depends on it:

| Change | Durable before |
|---|---|
| Next outbound sequence number | any message using it is written: an Idempotent receiver silently drops a number reused after a crash |
| A Recoverable message stored | it is written |
| An Idempotent message admitted | the handler sees it |
| A Recoverable message delivered, or skipped | nothing: recorded after the handler returns |
| A flow finishing or finished | the message announcing it is written |

A server also remembers the session IDs it negotiated, finalized ones
included, for the retention it is configured with, to reject their reuse.

## Limits

Every buffer is bounded: frame length (1 MiB by default), credentials,
reasons, messages kept beyond a gap, retransmission batch, sessions per
server, and the time Negotiate and Establish may take (the keepalive
interval by default, §7.1.7.6, §7.2.5.9). A malformed frame or message
ends the connection (§4.4). Logs and observers never show credentials:
an observer sees every frame of an established connection, before it is
handled or once written, a Negotiate's, a NegotiationResponse's or an
Establish's credentials zeroed whenever they come.

A Recoverable flow keeps its messages for retransmission up to a
retention target, the last N written (`MaxStoredMessages`), evicting the
older by batches; a peer asking for them is told they are no longer
available. Messages queued and not written are never evicted.

A session message, Applied and NotApplied included, is malformed, and
ends the connection (§4.4: "a transport should be terminated if an
unrecoverable error occurs in message parsing or framing"), when:

- its decoder refuses it, `codec.ErrNewer` among the errors: a newer
  version's groups or data the decoder cannot bound, nor know the meaning
  of (a FIXP message of a newer version holding data, as Terminate, is
  one: [docs/sbe.md](sbe.md#decoding)). A newer version's fixed fields,
  skipped by `blockLength`, are not;
- its frame holds bytes after what the decoder consumed, block padding
  counted. `TolerateTrailingBytes` accepts them when the header's version
  is not above the schema's, as Silverflash pads its session messages
  (see [the spike](#silverflash-spike)); after a newer version's message
  they may be its groups or data, refused either way. SOFH bounds the
  frame, not the message in it, and no SBE provision found forbids them:
  a validation policy kept strict by default ([docs/conformance.md](conformance.md));
- a required field holds its type's null, or an enumeration value is not
  one the schema lists (SBE §4.15): the message header's four fields,
  checked before anything acts on the message, codes, a Sequence's or a
  RetransmitRequest's sequence numbers and counts, timestamps, keepalive
  intervals. A `FlowType` is the negotiation's to answer
  (`FlowTypeNotSupported`); an optional field's null is its absence.

What the engine sends holds no null either: a keepalive interval is 2^32-2
ms at most (`KeepaliveInterval`, `MaxKeepalive`), a count 2^32-2
(`RetransmitBatch`; a gap one NotApplied cannot report terminates the
connection before anything is sent or recorded), and `SendApplied`
refuses its arguments' nulls (`ErrInvalidApplied`).

A server closes the connection on a malformed Negotiate or Establish,
unanswered; a client on a malformed answer, trying again; an established
connection terminates `UnspecifiedError`, with the reason.

## Where the standard contradicts itself

| Point | The text | The examples | fix2 |
|---|---|---|---|

The choices aim at messages a peer of either reading handles, and accept
what either reading sends, unless accepting would deliver messages wrongly
numbered or twice. Where no choice satisfies both, the text wins over the
examples. [docs/fixp-examples.md](fixp-examples.md) goes through every
example, with the tests that run it.

## Interoperability

The [Silverflash](https://github.com/FIXTradingCommunity/silverflash)
reference implementation (Java), at commit
`ef066d2ffd4d123763e226c7caca1a976041e9f7`, carries a copy of the schema
whose templates 1 to 18 match the pinned one; it lacks MessageTemplate
(19), which fix2 does not use. Its framing is configurable: SOFH has to
be chosen explicitly. It predates the standard's 2021 text, so its session
behaviour is checked against this document, not taken as a reference.
Interoperability results distinguish byte-level fixtures from live
sessions.

### Silverflash spike

A throwaway Go client, encoding the session messages by hand from the
pinned schema, ran against a Silverflash server built from that commit
with SOFH framing ([evidence](fixp-evidence/silverflash-spike/)). The
client negotiated an Idempotent flow, established, sent three messages,
stayed idle, skipped sequence numbers 4 to 9, terminated, and reconnected
to re-establish; with a Recoverable server flow, it was to ask for
retransmission too.

What agreed: the byte layout of Negotiate, NegotiationResponse, Establish,
EstablishmentAck, Sequence, NotApplied and Terminate, read both ways
between the hand encoding and Silverflash's codecs, which Real Logic's
`sbe-tool` 1.5.0 generates from its copy of the schema; implicit
numbering of the client's flow (Sequence 1, then 1 to 3; Sequence 10,
then 10); the server's Idempotent flow (a Sequence 1, then its replies
1 to 3); NotApplied from 4, count 6, on the gap, consuming the server's
sequence number 4, its next reply taking 5 (§4.8.2); the graceful
Terminate exchange. EstablishmentAck carries no `NextSeqNo` for an
Idempotent server flow, which the text allows (§4.3.2).

What did not:

- **SOFH length.** Silverflash's Message_Length excludes the 6-byte
  header; SOFH 1.0, and 1.1 RC1, define it as "the length in octets (i.e.
  bytes) of a message inclusive of the length of the Simple Open Framing
  Header". Neither side can read the other's frames: a standard SOFH
  Negotiate gets no answer. The rest of the spike ran with the client
  writing and reading Silverflash's length.
- **Recoverable server flow.** Establishment crashes Silverflash
  (`ClassCastException`: `RecoverableFlowSender` does not implement the
  `FlowSender` it is cast to): no Recoverable flow out of it, the pair the
  standard recommends included. Retransmission could not be tried.
- **Heartbeats.** Over 3.5 s without application messages either way,
  its keepalive interval being 1000 ms, the server sent no heartbeat; the
  client sent a Sequence every 500 ms (§4.5).
- **Padding.** Its session messages carry 4 to 6 zero bytes after the SBE
  message; its application messages do not.
- **Re-establishment: not tried.** The spike's server builds a new
  Silverflash session for every connection, without the negotiated one's
  state; an Establish on a new connection then crashes it
  (`NullPointerException`). That is the spike's harness, not a finding
  about Silverflash's re-establishment.
- **Toolchain.** It builds only after removing a deployment plugin from
  its POM and adding `javax.annotation-api` (its SBE generator's code
  needs it on Java 11 and later), runs on Apple silicon only with JNA 5
  in place of its JNA 4.2.2, and on Java 17 and later only with
  `--add-exports`/`--add-opens` for its Agrona.

Unpatched, Silverflash is no live interoperability peer for the profile
above: it cannot read or write standard SOFH frames, and cannot send a
Recoverable flow. Interoperability rests on, in order:

1. an independent SBE encoder, Real Logic's, generating codecs from the
   pinned schema, cross-checked byte for byte with `fix2gen sbe`'s;
2. wire fixtures: the standard's examples, and the frames the spike
   exchanged where both sides agreed, their SOFH length corrected;
3. live sessions against a peer found later, or a patched Silverflash
   (SOFH length, Recoverable sender), clearly labelled as such.

### Patched Silverflash, live

With its SOFH length patched to include the header
([evidence](fixp-evidence/silverflash-patched/)), Silverflash serves
fix2's client: negotiation, establishment with an Idempotent or a
Recoverable client flow, 2000 orders and their answers each way, paced by
windows of 50, and the Terminate exchange (`fixp/tests/silverflash`,
opt-in with `FIX2_SILVERFLASH`). Partial interoperability, with a patched
peer, and opt-in tests characterize what fails on its side: unpaced, its
consumer receives some hundreds of 2000 orders, then no more; it answers
our FinishedSending with a Terminate, unfinalized, and our
re-establishment kills its session thread, as does a Negotiate written in
two parts 50ms apart, its read buffer cleared before each read; it sends
no heartbeat, and pads its session messages: the tests set
`ToleratePeerWithoutKeepalives` and `TolerateTrailingBytes`. A Recoverable server flow, re-establishment of a live session,
retransmission, NotApplied and fix2's server against its client are not
exercised.

The spike's server first left its send buffers' position at zero, which
Silverflash's writer flips to empty: the replies and their Sequence were
lost or garbled. The evidence is from the corrected harness.

## Performance

On an Apple M4, Go 1.27, both ends in one process, a 64-byte application
message (`go test -bench . ./fixp/session/ ./fixp/internal/codec/
./internal/gen/sbe/...`):

| Path | Time | Allocations |
|---|---|---|
| Encoding or decoding a session message (Sequence, RetransmitRequest, Establish) | 2–5 ns | 0 |
| Classifying a frame | 2 ns | 0 |
| Encoding or decoding SBE's NewOrderSingle, ExecutionReport with two fills, a generated codec | 5–11 ns | 0 |
| `Send`, to the peer's handler, Unsequenced flow, TCP | 165–200 ns | 1 |
| `Send`, Idempotent flow, TCP | 320–340 ns | 3 |
| `Send`, Recoverable flow, stored in memory (the last 65536), TCP | 385 ns | 4 |
| A message and its echo, one at a time, TCP loopback | 28 µs | 9 |
| The same in memory | 7 µs | 28 (the in-memory transport's) |

`Send` is measured back to back, timed until the peer's handler has the
last, its writer and the peer's reader running alongside. The writer
writes in one write what the queue holds, application messages and their
Sequences, once the queue has no more, or once that holds 64 KiB or is a
quarter of a keepalive interval old; any other frame is written alone,
after them, but an urgent Terminate, which drops them, as a write failing
would. The store evicts messages once written, not once taken out of the
queue. A round trip is latency: four goroutine wakeups and two loopback
hops. `contribs/fixpecho` measures the same
over TCP between processes: 767,000 echoes a second with 100 messages
in flight, 20 µs a round trip at p50 one at a time.

What a message allocates: its frame, owned by the queue, encoded into a
pooled buffer and copied at its size; on a sequenced flow, the store
call's context, without a timer until a store asks for one; on a
Recoverable flow, the store's copy.
