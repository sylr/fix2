# Application messages over FIXP

How an application sends and receives its own messages over a FIXP
session of fix2 ([docs/fixp.md](fixp.md)): their codecs generated by
`fix2gen sbe` ([docs/sbe.md](sbe.md)) from the application's SBE schema,
the session carrying them opaque. `Example_applicationMessages`
([`fixp/session/example_app_test.go`](../fixp/session/example_app_test.go))
runs what follows, an order and its acknowledgement, with the codecs of
SBE's own examples; an application generates its own.

## The schema

The session reads every message's SBE header to classify it, and frames
what it sends as SBE 1.0 little-endian (SOFH encoding type `0xEB50`). The
application's schema must therefore:

- have `byteOrder="littleEndian"`, SBE's default;
- have a message header starting as SBE's standard one, with four
  `uint16`: `blockLength`, `templateId`, `schemaId`, `version`;
- not use FIXP's schema id, 2748: `Send` refuses such a message
  (`ErrSchema`), and on receipt it is a session message.

## Generating

    go run github.com/sylr/fix2/cmd/fix2gen sbe -schema orders.xml -pkg orders -out internal/orders

or, as a Go tool of the application's module (`go get -tool
github.com/sylr/fix2/cmd/fix2gen`), from a `//go:generate` line:

    //go:generate go tool fix2gen sbe -schema orders.xml -pkg orders -out .

The package holds a struct per message, with `AppendTo`, `Decode` and
`DecodeBody`, its template ID as a constant, and `SchemaID`,
`SchemaVersion`, `MessageHeader` and `ReadHeader` (see
[docs/sbe.md](sbe.md#generated-code)). Commit it, and check in CI that
generating again changes nothing.

## Sending

A generated message is a `session.Outgoing`: `Send` encodes it into a
frame of its own, behind the session's, and queues it.

```go
order := &orders.NewOrderSingle{Side: orders.SideEnumBuy, OrderQty: orders.QtyEncoding{Mantissa: 100}}
copy(order.ClOrdID[:], "ORD1")
seq, err := s.Send(ctx, order)
```

`Send` returns once the message is the flow's: numbered, stored on a
Recoverable flow, queued for the connection the session is established on
or the next one. It reads the struct during the call only: the struct may
be reused right after. `SendRaw` takes a message already encoded, its
header included, borrowed for the call. Encoding can fail: a data field
too long for its length type, or a group's entries out of bounds; `Send`
returns the codec's error then, and nothing is sent.

From a callback, `Send` does not wait for room in the queue: it fails
with `ErrQueueFull` instead (`Config.MaxPendingMessages`). A server
answering each message, as an exchange acknowledges orders, either
returns the error, which terminates the connection, or waits for room
with a context of its own, bounded, holding back the connection's reads:
[`contribs/fixpecho`](../contribs/fixpecho) does the latter.

## Receiving

`Handler.OnMessage` gets each application message whole, its SBE header
included, and its header read (`in.Header`). Check the schema first, then
decode by template:

```go
func (x *exchange) OnMessage(ctx context.Context, s *session.Session, msg []byte, in session.Inbound) error {
	if in.Header.SchemaID != orders.SchemaID {
		return fmt.Errorf("schema %d, not %d", in.Header.SchemaID, orders.SchemaID)
	}
	h, body, err := orders.ReadHeader(msg)
	if err != nil {
		return err
	}
	c := x.codecsOf(s) // this session's structs (see Allocation)
	switch h.TemplateId {
	case orders.NewOrderSingleTemplateID:
		if err := c.order.DecodeBody(h, body); err != nil {
			return err
		}
		...
	default:
		return fmt.Errorf("template %d unexpected", h.TemplateId)
	}
}
```

`Decode(msg)` does both at once, for a handler expecting one message
only. An error from `OnMessage` terminates the connection
(UnspecifiedError) and the message does not count as delivered: on a
Recoverable flow it is asked for again on the next establishment, on an
Idempotent one it was admitted, and is not delivered again (see [Delivery
guarantees](fixp.md#delivery-guarantees)). An application that rejects a
message on business grounds answers it with a message of its own schema
instead, such as a BusinessMessageReject.

A peer of a newer schema version may append fixed fields to a message:
they are skipped. It may not add groups or data fields to an existing
message and still be read correctly (see
[docs/sbe.md](sbe.md#decoding)); check `h.Version` against `SchemaVersion`
when that matters.

## Borrowed bytes

`msg` is borrowed for the call: the session reuses its buffer once the
callback returns. A decoded struct's `[]byte` fields, its data fields,
alias `msg`; its fixed fields and arrays are copies. A struct decoded
into again reuses its groups' slices, their entries overwritten. Keep
what outlives the callback, or the next decoding, as a copy of its own:
its `[]byte` fields cloned (`bytes.Clone`), its group slices cloned, and
theirs within, recursively; or decode the message again, into a struct
of its own, from a copy of `msg`.

## Allocation

A session's callbacks run one at a time, on its reader goroutine; a
server's sessions run theirs concurrently. A handler may keep one struct
per message type per session, and decode into it again: once warm,
decoding allocates nothing, groups reusing their slices' capacity. A
handler serving several sessions, as a server's does, keeps them per
session, not in itself. `Send` allocates the frame it queues, one per
message; benchmarks ([increment M9](fixp.md#increments)) measure the
session's paths.

## Applied and NotApplied

Applied and NotApplied are application messages of FIXP's schema, which
the session sends and delivers itself: `Session.SendApplied`, and
`Handler.OnApplied` and `OnNotApplied`. On an Idempotent flow, a message
NotApplied reports never reached the peer; sending it again, under a new
sequence number, is the application's choice.
