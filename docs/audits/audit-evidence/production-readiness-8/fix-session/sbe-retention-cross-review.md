# Independent source cross-review: generated SBE group retention

Reviewed HEAD `c7e5579`, the proposed `group-retention_test.go.txt` and `group-version-retention_test.go.txt`, their saved race output, generator emission, tracked rich/newer codecs, and the documented borrowed-input/reuse contract.

The finding is valid. `internal/gen/sbe/gen.go:1097` emits a zero-count branch that only reslices to length zero. Line 1113 similarly shrinks a nonempty group without clearing discarded entries. The version-absent branch at line 1302 only reslices. Retained backing-array elements therefore retain their byte-slice pointers and nested group slices. Go's garbage collector scans the complete allocated backing array, regardless of the length of the public slice referring to it. They keep old input allocations live.

This is distinct from intentional reuse of the entry array's capacity. The reproduction keeps one generated Order and supplies distinct, short valid input frames. As the group shrinks one entry at a time, each just-discarded entry still points into a different previous frame. A final public group of length zero therefore retains hundreds of historical input buffers, rather than only the high-water entry array and the current input. The constant-count control repeatedly overwrites every entry, retaining approximately one input frame and the entry array. Exact heap-byte deltas are runtime-sensitive; the structural check of 512 removed entries still holding nonempty Note slices directly establishes the cause, independent of those deltas.

The diagnostic uses tracked generated codec source unchanged, successful whole-message decoding, and a realistic valid API usage pattern. Fresh input buffers are allowed: docs/sbe.md says decoded DATA aliases the caller's input; neither that document nor docs/fixp-app.md forbids new allocations per message. No stale input bytes are read after a caller invalidates them. The version-absent diagnostic independently shows the same issue for a nested group. Its zero-value reset control confirms a caller workaround, not an existing generated cleanup facility.

P3 is the defensible severity from this evidence. It demonstrates avoidable retained-memory amplification and contradicts a simple per-message allocation-bound interpretation, but does not demonstrate process OOM, a live exchange attack, an indefinitely growing leak for a fixed bounded shape, data corruption or a FIXP transport outage. This history has a finite number of retained slots for a fixed set of capacities. If a caller reuses the same input backing allocation, those slots mostly alias that same allocation and this particular historical-frame amplification disappears. Higher schema limits, more decoder instances and nested historical capacities can increase the practical memory cost; do not equate MaxEntries on one decode with a global bound on all historical capacities retained by a reused struct.

Acceptance should sever references from discarded entries on count decrease, zero count and version absence, recursively or by zeroing entire discarded entry structs. Preserve capacity reuse where practical and avoid merely documenting retention as required for zero allocations: clearing references in removed elements does not inherently require a new allocation. Keep allocation tests and successful decoding/round-trip tests, plus a structural removed-tail test so that GC heuristics are not the primary regression oracle.
